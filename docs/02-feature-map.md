# PantryChef — карта функций

Полный перечень функций системы с приоритетами по **MoSCoW**:
**Must** — без этого продукт не работает и смысла не имеет; **Should** — то, что делает цикл удобным и удерживающим; **Could** — рост после стабилизации ядра; **Won't** — сознательные отказы (почему — в [концепции, раздел 7](./01-concept.md#7-чего-мы-сознательно-не-делаем)).

Правило: новая функция попадает в бэклог, только если она усиливает ежедневный цикл «пополнение → идея → готовка → спасение» или снижает трение внутри него.

## 1. MUST — первая волна (рабочий продукт)

| # | Функция | Что это | Какую боль закрывает |
|---|---|---|---|
| M1 | **Холодильник (инвентарь)** | Список продуктов: название, категория, количество, срок годности, место (холодильник / морозилка / кладовая). Поиск, фильтры по свежести и категориям | «Что у меня вообще есть?» |
| M2 | **Ручное добавление за секунды** | Название → AI подставляет категорию и типичный срок («не знаешь — оставь как есть»), простой степпер количества | Страх «завести данные и потом поддерживать» |
| M3 | **Статусы свежести** | Четыре состояния: Свежо / Скоро (2–3 дня) / Спасаем (сегодня–завтра) / Просрочено — цветовые бейджи, единые для всего приложения | Продукты «теряются из виду» |
| M4 | **Три идеи на сегодня** | AI подбирает 3 блюда из имеющихся продуктов; приоритет — спасаемое; у каждой идеи объяснение «почему она» | Ежедневное «что приготовить?» |
| M5 | **Карточка рецепта** | Фото, время, порции, сложность; ингредиенты с отметкой «есть / нет»; шаги; действия: готовить, в план, в избранное | Разрыв между идеей и готовкой |
| M6 | **Режим готовки** | Полноэкранный пошаговый режим: крупный текст, таймеры в шагах, экран не гаснет, свайп вперёд/назад | «Телефон в руках, руки в тесте» |
| M7 | **Автосписание** | После готовки — подтверждение списком «что использовали» (всё отмечено по умолчанию) → холодильник обновляется сам | Данные устаревают за неделю, приложение умирает |
| M8 | **Список покупок** | Ручное добавление + «добавить недостающее из рецепта»; группировка по отделам магазина; чекбоксы; «купили» → предложение пополнить холодильник | Разрыв между рецептом и магазином |
| M9 | **Спасаем сегодня** | Отдельный блок на главном экране + действие у каждого «спасаемого» продукта: приготовить / заморозить / съесть | Анти-отходы: ядро ценности для экономных |
| M10 | **Причины списания** | Списать можно с причиной: приготовлено / выброшено / съедено как есть / заморожено (продлевает срок) | Честная статистика и морока с «куда делось» |
| M11 | **Аутентификация** | Email + пароль, вход через соцпровайдеров, 2FA (OTP). Уже частично реализовано | Данные должны жить в облаке и синхронизироваться |
| M12 | **Push «Спасаем» и «План пуст»** | web-push: одно уведомление утром при истекающих продуктах; напоминание о пустом плане в день закупки. Политика — в UX-спеке, раздел 6 | Напоминание в нужный момент, без спама |
| M13 | **PWA + темы** | Установка на главный экран; светлая/тёмная тема без мигания. Уже реализовано | Мобильное ощущение без сторов |
| M14 | **Пустые и ошибочные состояния** | Осмысленные состояния каждого экрана: пустой холодильник, мало продуктов для идей, ошибка AI с повтором | «Белый экран» убивает доверие мгновенно |

## 2. SHOULD — вторая волна (удобство и удержание)

| # | Функция | Что это | Зачем |
|---|---|---|---|
| S1 | **Сканер штрих-кодов** | Камера + база штрих-кодов: отсканировал → продукт в холодильнике | Ввод после закупки — самая частая операция |
| S2 | **Фото полок (AI-распознавание)** | Сфотографировал полку → приложение предлагает распознанные продукты пачкой с подтверждением | Главный «нулевого трения» ход; вау-момент онбординга |
| S3 | **План на неделю** | Сетка 7 дней × приёмы пищи (ужин всегда, обед — опционально); перенос рецептов в слоты; слот пуст — подсвечен | Снимает решения разом, а не ежедневно |
| S4 | **Генерация плана из холодильника** | «Заполнить неделю» — AI составляет план, приоритет спасаемому и скоропортящемуся | Планирование без усилия |
| S5 | **Список покупок из плана** | «Чего не хватает на все блюда недели» → одним списком с учётом имеющегося | Одна закупка вместо трёх |
| S6 | **Итог закупки** | После магазина: «Отметить купленное» → маппинг в продукты с типичными сроками | Замыкание цикла без ручного набора |
| S7 | **Заморозка** | Действие «заморозить»: продукт переезжает в морозилку, срок продлевается по категории | Спасение без готовки |
| S8 | **Избранное и история готовок** | Понравившиеся рецепты; история «что и когда готовили» | Повтор удачного ужина одним тапом |
| S9 | **Профиль домохозяйства** | Состав семьи (сколько едоков) → порции в рецептах, планах и списках | «Семейный» расчёт без настройки каждый раз |
| S10 | **Статистика кухни** | Приготовлено / спасено / выброшено за период; серия «дней без выброшенного»; приблизительная оценка сэкономленного | Мотивация экономного; зеркало кухни |
| S11 | **Офлайн-режим** | Последние холодильник, план и список покупок доступны без сети (PWA-кэш) | В магазине связи может не быть |
| S12 | **Экспорт списка покупок** | Текстом в мессенджер/заметки | «Дорогой, купи…» без общего аккаунта |
| S13 | **Настройки уведомлений** | Переключатели по типам пушей + время утреннего напоминания | Контроль вместо «отключить всё» |
| S14 | **Быстрое списание** | Свайп по продукту: «съел яйцо» → минус одно, за полсекунды | Поддержание свежести данных между готовками |

## 3. COULD — третья волна (рост и отличия от конкурентов)

| # | Функция | Что это | Комментарий |
|---|---|---|---|
| C1 | **Общий холодильник (семья)** | Несколько участников домохозяйства видят один холодильник, план и список покупок в реальном времени | Самый сильный кандидат второй волны для «семей»; требует синхронизации и прав |
| C2 | **Чек как источник (OCR)** | Фотография чека → распознанные покупки → подтверждение | Дешевле штрих-кодов по усилиям, но требует OCR и терпимости к ошибкам |
| C3 | **Голосовой ввод** | «Добавить полкиро огурцов» | Удобно с грязными руками; зависит от качества распознавания |
| C4 | **Пищевая ценность (КБЖУ)** | Справочно в карточке рецепта и идеи | Не центр продукта (аудитория — не счётчики калорий), но спрос будет |
| C5 | **Диеты и аллергии** | Жёсткие фильтры генерации: без мяса, без глютена, аллергены исключены навсегда | После C4; важна, если придёт ЗОЖ-аудитория |
| C6 | **Режим «остатки»** | Отдельный сценарий: «у меня варёная гречка и кусок курицы» → блюда из полуфабрикатов | Точная боль донашивания; требует отдельного промпта |
| C7 | **Виджет на главный экран** | PWA-виджет «Спасаем сегодня: 3 продукта» | Держит ритуал без открытия приложения |
| C8 | **Напоминание по геолокации** | Возле магазина → пуш «не забудь список: 9 позиций» | Требует фоновую геолокацию — осторожно с приватностью и батареей |
| C9 | **Бюджет закупки** | Оценка стоимости списка, фактов выброшенного в деньгах | Цены магазинов ненадёжны; начать с приблизительной оценки по категориям |
| C10 | **Сезонные подсказки** | «Клубника в сезоне и дешёвая» в идеях и плане | Лёгкий слой поверх генерации |
| C11 | **Шеринг рецепта** | Ссылка/карточка рецепта для отправки | Органическое привлечение |
| C12 | **Структура полок** | Отображение по реальным полкам холодильника | Приятно, но усложняет ввод; сначала место хранения (3 варианта), потом полки |
| C13 | **Истечение по категориям-исключениям** | «У нас этот соус живёт вечно» — пользовательская правка типичных сроков | Уточнение M2, когда наберётся обратная связь |

## 4. WON'T — сознательные отказы

| Что не делаем | Почему |
|---|---|
| Соцсеть: ленты, подписки, комментарии, конкурсы | Размывает утилитарное ядро; мы не развлечение |
| Доставка продуктов, интеграции с ритейлом, цены в реальном времени | Чужая операционка; зависимость от внешних API убивает надёжность |
| Счётчик калорий как основа продукта | Другая аудитория и другой ежедневный ритуал; C4 — справкой, не центром |
| Видеокурсы, «станьте шефом», геймификация ради геймификации | Не наш ритуал; единственная допустимая «игра» — серия S10, потому что она про реальный результат |
| Требование идеального инвентаря, «аудит» и наказания за неточность | Противоречит принципу 2 концепции; точность — враг принятия |

## 5. Зависимости

- **M4–M7 (идеи, готовка, списание)** зависят от **M1–M3** (инвентарь): без актуального холодильника AI не имеет входа.
- **S3–S5 (план)** опираются на **M4–M5** (идеи и рецепты) и **M1** (что уже есть).
- **S6 (итог закупки)** опирается на **S1/S2** (скан) — иначе маппинг руками.
- **C1 (семья)** опирается на **M11** (аккаунты) и завершённый **S3–S5** (план).
- **C4→C5**: сначала пищевая ценность, потом жёсткие диетические фильтры.
- **S10 (статистика)** возможна только при работающем **M7 + M10** (автосписание с причинами) — данные копятся с первого дня, показываем позже.

## 6. Порядок выпуска

1. **Релиз 1 — «Цикл работает» (Must).** Холодильник + идеи + готовка с автосписанием + список покупок + пуши. Продукт полезен каждый день даже при ручном вводе.
2. **Релиз 2 — «Ввод лёгкий, неделя планируется» (Should 1–9).** Скан, фото полок, план недели, закупка в один заход, статистика.
3. **Релиз 3 — «Продукт растёт» (Could по результатам).** Семья, чек, диеты — по данным о том, чем реально пользуются.
